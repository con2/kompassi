# Kompassi authentication consumer inventory

Compiled 2026-08-04, ahead of eventually replacing Kompassi with a self-hosted open-source IAM. Covers every known app that authenticates against Kompassi, which of the old legacy OAuth2 flow or the newer OIDC flow each one uses, whether it depends on Kompassi's legacy `/api/v2/people/me` REST profile endpoint, and how each one uses Kompassi groups for access control.

### Not user-login OAuth/OIDC, but still Kompassi-coupled

- **Diskompassi** — Discord bot, polls legacy `/api/v1/events/{slug}/discord` with static HTTP Basic Auth, maps Kompassi roles to Discord guild roles. Server-to-server, no user login flow.
- **Kirppu** also has a _second_, separate legacy v1 Basic-Auth API client (`kompassi_crowd`) for an admin-side "look up this Kompassi username" feature, unrelated to its OAuth2 login flow.

## Group usage taxonomy

What matters for picking a replacement IAM: it needs to support all of these, not just a simple "is staff" flag.

1. **Hard login gate only** (must be in group X to sign in at all): Konsti, Infotv-tracon, Tracontent-premium, Outline.
2. **Admin/staff boolean derived from flat membership check**: Edegal, Infotv-tracon, Tracontent-premium, Infokala-tracon, Outline.
3. **Per-event/role templated group names** (most demanding): Infokala-tracon's `{installation}-{event_slug}-labour-*` templates.
4. **Full group-list mirroring** into the app's own permission model, syncing add/remove: Outline only — no other app does this.
5. **No group usage at all**: Kirppu (authz is local DB roles), Rallly-con2, Larpit-fi.

**Implication**: a replacement IdP needs a real multi-valued `groups` claim (or equivalent per-user group-list lookup), not just a boolean claim — patterns 3 and 4 both need the full list. Kompassi's current model (arbitrary string group name, many per user, reused across unrelated apps) is the shape everything today is built on.

## Common blockers for the legacy Django apps

Edegal, Kirppu, Infokala-tracon, Infotv-tracon, and Tracontent-premium all hand-roll `requests_oauthlib.OAuth2Session` against the same vendored `kompassi_oauth2` library, with no ID-token/OIDC support at all. None of them get an easy "flip a flag" migration — all would need swapping to something like `mozilla-django-oidc` and re-deriving group logic from claims instead of a REST call. Tracontent-premium additionally pulls Kompassi-specific profile fields (`nick`, `preferred_name_display_style`) with no OIDC standard-claim equivalent.

Konsti's blocker is different: it stores Kompassi's legacy numeric `Person` ID as `kompassiId: number` and queries by it directly — OIDC's `sub` claim is a different ID space, so the user model/repository would need to change, not just the login code.

## Notes (out of scope for this inventory, worth keeping on file)

1. **Desucon.fi runs its own OAuth2 provider** ("Desuprofile", via `django-oauth-toolkit`, legacy-only — no `OIDC_ENABLED`), and **Kompassi is the client**: `desuprofile_integration/` in this repo is a real, still-present Django app (models, views, migrations, wired into `kompassi/urls.py`), so "Login with Desuprofile" appears to still be a live option on Kompassi today, feeding Kompassi's own `Person`/`User` records. So the actual identity chain for this whole ecosystem runs **Desucon.fi (Desuprofile) → Kompassi → every app in the table above**. Desucon.fi's provider code returns almost the exact same field shape as Kompassi's own legacy `/api/v2/people/me` — same author, confirmed shared lineage. Out of scope for the current migration (we are not migrating desucon.fi's own IdP), but worth remembering it's the historical root, not an unrelated bystander.
2. **Kirppu is deployed twice with two different auth backends.** `kirppu.tracon.fi` uses `KompassiOAuth2AuthenticationBackend` as inventoried above. `kirppu.desucon.fi` instead receives a short-lived (15s), HS256-signed JWT SSO handshake from desucon.fi (`KIRPPU_SHARED_KEY`, dispatched from a `/kirppu/` consent view on desucon.fi to `https://kirppu.desucon.fi/desu_auth/`) — separate from Kompassi entirely. The receiving side lives in a separate repo, [kcsry/desukirppu](https://github.com/kcsry/desukirppu). Out of scope for the Kompassi migration, but a distinct integration worth remembering if desucon.fi's own auth ever changes.
3. **"Atlasso"** has a registered Kompassi OAuth2 client per infrastructure Ansible vars (`atlasso_kompassi_oauth2_client_id/secret`) but no local working copy was available to inspect when this was compiled.
4. Excluded as a false positive: Harakka's "OAuth" code is Google/Supabase auth, unrelated to Kompassi.
